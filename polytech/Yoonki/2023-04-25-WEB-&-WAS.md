# 3-Tier 아키텍처: 웹 서버(Web) vs WAS

현대의 모든 엔터프라이즈급 상용 웹 어플리케이션(쇼핑몰, 은행 서버 등)은 구조적 확장성과 장애 격리를 위해 역할을 3단계의 계층(Web - WAS - DB)으로 찢어놓는 **3-Tier 아키텍처**로 서버를 설계합니다.

이때 가장 헷갈리는 앞단의 두 가지 서버 엔진의 차이를 구분해야 합니다.

---

## 1. Web 서버 (웹 서버)
클라이언트(브라우저)와 1선에서 직접 대면하며, 계산이 필요 없는 사진이나 글씨를 갖다주는 고속 우체부입니다.

* **주역할:** HTML, CSS, JavaScript, 이미지 이미지(JPG) 등 연산이 필요 없는 멈춰있는 **정적(Static) 파일**을 가장 빠르게 꺼내서 클라이언트에 던져줍니다.
* **보안/로드밸런싱:** WAS가 고장 나거나 해킹당하는 것을 막기 위해 앞에서 리버스 프록시(Reverse Proxy)로 문지기 역할을 수행합니다.
* **대표 소프트웨어:** **Nginx, Apache HTTP Server** 등

## 2. WAS (Web Application Server)
DB의 데이터를 조회해서 화면을 꾸미거나, 결제를 처리하는 등 브레인(두뇌) 연산을 전담하는 공장입니다.

* **주역할:** 사용자가 "내 장바구니 리스트를 보여줘!" 라고 요청하면, 단순 파일 스토리지에 없으므로 DB를 쿼리해서 정보를 빼내고 프로그래밍 로직(Java, Node.js 등)을 돌려 나만의 웹페이지(HTML)를 **동적으로 생성(Dynamic)**해 반환합니다.
* **대표 소프트웨어:** **Tomcat (톰캣), JBoss, WebLogic**, NodeJS, Django, Spring Boot 내장 엔진 등

## 3. 왜 합치지 않고 굳이 찢어놓을까요? (실무 협업 아키텍처)

초창기에는 톰캣(WAS) 하나에 다 때려박고 정적 파일과 동적 파일을 한 번에 돌렸습니다. 그런데 왜 요즘은 맨 앞에 Nginx를 꼭 세워둘까요?

### 1) 퍼포먼스(속도)의 분업화
WAS는 DB를 조회하고 복잡한 프로그래밍 코드를 돌리느라 CPU가 쉴 틈이 없습니다. 그런데 이 복잡한 WAS에게 단순 이미지 사진 100장을 뿌리라는 심부름까지 시키면 서버가 과부하로 터집니다. 따라서 "멍청하지만 속도는 초당 수만 장씩 파일을 던져주는 천재인" Nginx를 맨 앞에 세워, 사진 파일 요청은 자기가 다 받아먹고 튕겨내게 **캐싱 분산**을 걸기 위함입니다. 

### 2) 무중단 운영 (로드밸런싱)
쇼핑몰 이벤트를 해서 접속자가 터지면 Nginx 웹 서버 뒤에 Tomcat 1번, 2번, 3번 서버를 다중으로 연결시킵니다. 만약 1번 Tomcat에 에러가 나서 뻗어버려도, 앞단에 살아있는 Nginx가 재빠르게 "1번 죽었네, 2번 서버로 보내!" 하고 트래픽을 넘겨버리면 사용자는 서비스 마비를 전혀 눈치채지 못합니다. (L7 로드 밸런싱 구조 구현)
