# 정적 페이지(Static) vs 동적 페이지(Dynamic)

우리가 매일 사용하는 모든 웹 사이트는 클라이언트(브라우저)에게 문서를 던져주는 방식에 따라 크게 '정적 페이지'와 '동적 페이지' 두 가지로 나뉩니다.

---

## 1. 정적 페이지 (Static Web Page)

서버의 폴더 안에 이미 작성해 둔 HTML 파일이나 JPG 이미지를, 누가 요청하든 **있는 그대로 똑같이 꺼내어 보여주는 페이지**입니다.

* **동작 원리:** 사용자가 요청하면 맨 앞단의 우체부인 **Web Server (Nginx, Apache)**가 자신의 하드디스크 창고(`/var/www/html`)를 뒤져서 파일을 그대로 반환합니다.
* **장점:** DB를 조회하거나 연산을 하는 과정이 아예 없기 때문에 렌더링 속도가 빛의 속도입니다. 서버 부하도 가장 적어 CDN을 붙여 서빙하기 좋습니다.
* **단점:** 네이버 블로그 포스팅처럼 글 하나를 쓸 때마다 무조건 물리적인 새로운 HTML 파일 하나를 새로 작성해 올려야 하므로 서비스 관리가 불가능에 가깝습니다.

## 2. 동적 페이지 (Dynamic Web Page)

누가, 언제, 어떤 상황에서 요청했는지에 따라 서버가 실시간으로 데이터를 조합하여 **서로 다른 내용의 결과를 찍어내어 보여주는 페이지**입니다.

* **동작 원리:** 사용자가 "내 장바구니 리스트를 보여줘!" 라고 요청하면, 단순 웹 서버는 처리하지 못하므로 뒷단의 **WAS (Web Application Server, 톰캣 등)**에게 토스합니다. WAS는 DB 서버에 접속해 내 아이디에 일치하는 상품 리스트를 뽑아온 뒤 동적인 HTML 결과물을 즉석 조립해서 반환해 줍니다.
* **장점:** 똑같은 `cart.html`을 요청해도, 접속한 내 계정이 무엇이냐에 따라 화면이 변합니다. 수만 페이지의 방대한 게시판이나 쇼핑몰 로직 등 관리 자동화가 가능합니다.
* **단점:** 연산을 많이 하므로 속도가 미세하게 느리며, 다량의 트래픽이 몰리면 DB 커넥션 병목이나 CPU 과부하 창구가 됩니다.

---

## 3. 웹 서버(Web)와 WAS(어플리케이션 서버) 분리 아키텍처

현대의 중대형 서비스들은 정적 처리를 전담하는 앞단의 **웹 서버(Web)**와 동적 처리를 전담하는 뒷단의 **응용 서버(WAS)**를 굳이 물리적으로 쪼개서 구성합니다.

1. **부하 방지와 효율적 분산:**
   연산이 빡센 동적 쿼리 처리는 WAS(Tomcat/Spring)가 뒤에서 묵묵히 전담하고, 변경되지 않는 CSS나 이미지 사진 수천 장 뿌리는 허드렛일은 앞단의 Web Server(Nginx)가 혼자 다 받아치게 일을 나누어 서버 뻗음을 막습니다.
2. **보안성 강화 (리버스 프록시):**
   외부 인터넷 해커들은 앞문의 방패인 Web Server의 포트(80, 443)만 타격할 수 있고, 고객의 개인정보가 들어있는 최종 DB와 직접 맞닿은 핵심 WAS 서버는 내부망 깊숙히 감춰 방화벽 안전지대를 형성할 수 있습니다.
3. **무중단 스케일 아웃 (장애 극복):**
   WAS 1대가 고장 나서 멈춰도 앞단 웹 서버(로드 밸런서)가 생존해 있으므로, 즉시 오류 요청을 차단하고 2번 WAS 컴퓨터로 우회하여 트래픽을 흘려 무중단 패치를 가능하게 합니다.
