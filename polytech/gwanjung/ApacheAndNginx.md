# 웹 서버의 양대산맥: Apache vs Nginx

세계 웹 서버 시장을 양분하는 핵심 소프트웨어인 아파치(Apache)와 엔진엑스(Nginx)는 겉보기엔 똑같이 HTTP 요청을 처리해 주지만, 내부를 들여다보면 엔진 구조와 처리 패러다임이 완전히 다릅니다.

## 1. Apache (프로세스/스레드 기반 아키텍처)
1995년부터 웹의 역사를 함께 해온 전통의 강자입니다. 

### 구동 방식 (MPM: Multi-Processing Module)
아파치는 손님(클라이언트)이 접속할 때마다 종업원(프로세스나 스레드)을 1:1로 새롭게 배정해 응대하는 방식을 씁니다.
1. **Prefork 방식:** 손님이 올 때마다 아예 프로세스를 통째로 복제해서 할당합니다. 안정성은 최고지만, 접속자가 1만 명이 되면 프로세스 1만 개가 생성되어 서버 메모리가 과부하로 터져버리는 최악의 단점이 있습니다.
2. **Worker 방식:** 메모리 낭비를 줄이기 위해, 하나의 프로세스 안에 가벼운 스레드(Thread)를 여러 개 생성해 응대합니다. 하지만 접속자가 폭증하면 CPU가 스레드 교체(Context Switching)를 하느라 역시 뻗어버리는 한계를 지닙니다. (이를 **C10K 문제**라고 불렀습니다.)

---

## 2. Nginx (비동기 이벤트 기반 아키텍처)
러시아 개발자가 아파치의 "C10K 문제(동시 접속자 1만 명 이상의 병목 현상)"를 완벽히 해결하기 위해 2004년에 내놓은 최신 아키텍처입니다. 현대 인프라에서는 아파치를 밀어내고 표준으로 자리 잡았습니다.

### 구동 방식 (Event-Driven)
종업원 1명(Worker Process)이 수천 명의 손님 주문을 동시에 받아놓고 대기표를 뽑아주며, 요리가 완성되는 순서대로 바로바로 빠르게 서빙(비동기 이벤트콜백)해버리는 마법 같은 구조입니다.

* **Master Process 1개:** 설정 파일을 읽고 조율합니다.
* **Worker Process N개 (보통 CPU 코어 수만큼 고정):** 단 한 개의 프로세스가 수천, 수만 개의 HTTP 연결(이벤트)을 큐에 올려놓고 쉴 새 없이 빙글빙글 돌며(Loop) 처리합니다.
* **메모리의 혁명:** 손님이 만 명이 오든 십만 명이 오든, 프로세스는 고정된 개수만 존재하므로 메모리 사용량이 일정한 상태를 유지합니다. 엄청난 퍼포먼스와 스케일 아웃이 가능합니다.

### ❓ 스레드 풀 (Thread Pool)의 도입
비동기로 수만 개의 요청을 번개처럼 처리하는 워커 프로세스에게 "기가바이트 짜리 대형 파일 읽어줘(Disk I/O)"라는 무거운 블로킹 작업이 들어오면 어떻게 될까요? 워커가 그 파일을 읽는 수십 초 동안 뒤에 있던 수천 명의 접속자가 모두 대기하는 치명적인 병목이 발생합니다.
따라서 최신 Nginx는 이런 무거운 파일 읽기 작업만 전문적으로 뒤로 빼돌려서 처리하는 **스레드 풀(Thread Pool)**이라는 별동대를 배치하여 결점을 완벽히 극복했습니다.
