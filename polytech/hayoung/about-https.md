# HTTP의 죽음과 HTTPS 암호화 (SSL/TLS)의 등장

**HTTP**는 웹 브라우저(크롬)가 웹 서버와 문서를 주고받는 가장 기초적인 통신법입니다.
하지만 옛날 HTTP는 엽서 통신과도 같았습니다. 우리가 네이버에 로그인할 때 입력하는 아이디와 암호 정보가 '평문(Plaintext)'으로 공기 중을 날아가 기지국을 통과하기 때문에 누구나 엽서를 훔쳐 읽듯 내 해킹이 가능했습니다.

이에 대한 극약 처방으로 **"자물쇠로 잠근 봉투에 통신문을 담아 안전하게 전송하자"**며 둔갑시킨 보안 프로토콜이 바로 **HTTPS (Secure)** 이며, 구글(Google) 마저 HTTPS를 지원하지 않는 모든 일반 사이트에 `주의 요함` 경고를 박아버리는 강력한 표준화 정책으로 인해 현대 웹은 100% HTTPS 시대로 도래했습니다.

## 1. 암호화의 딜레마 (대칭키 vs 공개키)
HTTPS가 탄생하기 위한 가장 핵심 로직은 비밀번호 통신을 어떻게 숨기느냐입니다. 

### 딜레마 1: 대칭키 암호화 방식
* **설명:** 비밀번호 A("1234")로 서류를 암호화해서 날려 보냅니다. 받는 사람도 암호 A("1234")로 서류를 복호화해야 합니다.
* **장점:** 연산 속도가 엄청나게 빠릅니다.  
* **문제점:** 자물쇠통과 열쇠를 같이 보내는 꼴입니다. 중간에 해커가 열쇠(A)마저 훔치면 암호가 무용지물이 됩니다.

### 딜레마 2: 공개키 (비대칭키) 암호화 방식
* **설명:** '개인 키'와 '공개 키'라는 암호 키 두 개를 만듭니다. 서버는 나의 '개인 키(비밀 금고 열쇠)'는 숨겨두고, '공개 키(열려있는 금고 상자)'만 인터넷에 천 장 뿌립니다.
클라이언트는 서버가 뿌린 '공개 키' 상자 안에 데이터를 넣고 탁 닫아버립니다. 닫힌 상자는 전 세계 누구도 못 열고, 오직 서버에 꽁꽁 숨겨둔 단 하나의 '개인 키'로만 박스를 딸 수 있습니다.
* **문제점:** 보안성은 지구상 최고 수준으로 완벽하지만, 연산이 더럽게 깁니다. 수 기가바이트 넷플릭스 영화 트래픽을 비대칭키로 연산하면 컴퓨터 CPU가 타들어 갑니다.

## 2. HTTPS의 천재적 솔루션 (하이브리드 암호화 과정)
결국 SSL/TLS 통신은 **"이 두 가지 방식을 섞자!" (대칭키의 속도 + 공개키의 보안)** 라는 천재적인 하이브리드 발상을 도입했습니다. 다음과 같이 물 흐르듯 진행됩니다.

1. **[Handshake 시작]** 클라이언트(브라우저)가 서버(네이버)에 최초 접속합니다.
2. 서버는 자신의 '공개키'가 담겨있고 이 서버가 진실한 곳임을 공인 기관(CA)이 보증한 신분증(=**SSL 인증서**)을 던져줍니다.
3. 클라이언트는 내 PC에 내장된 인증 기관(CA) 목록을 스캔해, 네이버가 짭이 아닌 진짜임을 확인합니다!
4. **[핵심 하이브리드]** 클라이언트는 즉석에서 **내 PC가 만든 초고속 '대칭키(랜덤 비밀번호)'**를 하나 뽑아냅니다. 그러고는 네이버가 아까 준 '공개키' 금고 상자에 대칭키만 싹 넣고 문을 닫아 네이버 서버로 쏴버립니다. 
5. 중간에 해커가 훔쳐도 네이버 전용 상자라 못 엽니다. 네이버는 숨겨둔 '개인키'로 상자를 따 열어 클라이언트가 보낸 빠른 대칭키를 손에 쥡니다.
6. **[통신 성사]** 이제 네이버와 내 PC는 서로 똑같은 초고속 '대칭키'를 안전하게 은밀히 나눠 가졌습니다. 이후부터는 웹 서핑 끝날 때까지 이 대칭키로 양측이 번개같이 서류를 암호화해서 영화도 보고 메일도 보냅니다.
