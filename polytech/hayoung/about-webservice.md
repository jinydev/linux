# 웹 서비스 (Web Service) 아키텍처: SOAP vs REST

기업과 기업, 혹은 프로그램과 프로그램끼리 데이터를 주고받기 위해서는 표준화된 통신 규약과 포맷이 필요합니다. 이를 가능하게 하는 소프트웨어 시스템을 **웹 서비스(Web Service)**라고 부릅니다. 

과거와 오늘날, 이 웹 서비스를 구현하는 2가지 거대한 패러다임이 있습니다.

---

## 1. 과거의 엔터프라이즈 거인: SOAP 기반 웹 서비스
> (Simple Object Access Protocol)

2000년대 초중반, 무조건 철저하고 견고한 은행권이나 대기업 시스템 통신을 위해 만들어진 극도로 복잡하고 거대한 규칙 체계입니다. 전적으로 **XML** 포맷만 취급합니다.

* **WSDL (Web Service Description Language):** 마치 두꺼운 제품 매뉴얼처럼, 상대방 시스템에 "나한테는 이런저런 기능이 있고, 호출하려면 정확히 이런저런 타입의 변수를 던져야 해"라고 설명해두는 계약서입니다.
* **UDDI:** 그런 WSDL 매뉴얼들을 모아놓은 글로벌 전화번호부 책입니다.
* **단점:** 봉투(Envelope)라는 복잡한 XML 헤더를 매번 씌워야 해서 데이터 덩치가 너무 커지고, 처리 속도가 느리며 구조가 지나치게 딱딱합니다. 오늘날 가벼운 모바일앱 기반 서비스에는 거의 쓰지 않는 '무거움'의 대명사가 되었습니다.

## 2. 현대 마이크로서비스(MSA)의 표준: RESTful API
> (REpresentational State Transfer)

SOAP의 그 무겁고 거대한 XML 덩어리에 진절머리가 난 현대 개발자들이 "HTTP 본연의 단순한 디자인(GET/POST/PUT/DELETE)을 그대로 살려서 직관적으로 통신하자"고 합의한 설계 철학입니다.

* **포맷:** 지저분한 XML 대신, 사람과 기계 모두가 읽기 편한 극도로 가벼운 **JSON (JavaScript Object Notation)** 포맷을 99% 사용합니다.
* **특징:** UDDI 같은 거창한 전화번호부나 WSDL 계약서가 강제되지 않습니다. (대신 Swagger 등을 가볍게 씁니다.)
* **장점:** 빠르고 유연하며 다루기 쉽습니다. 현재 전 세계 아마존(AWS), 구글, 카카오, 넷플릭스의 외부 통신 99%는 이 RESTful 비즈니스 구조를 기반으로 돌아갑니다.

> 💡 **요약:** 과거의 복잡한 3대장(SOAP, WSDL, UDDI)은 유지보수되는 구형 금융권 코어 시스템에나 남아있으며, 오늘날의 웹 서비스는 **[ REST 아키텍처 + JSON 포맷 ]** 체계로 완전히 통일되었습니다.
