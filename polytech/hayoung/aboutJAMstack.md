# JAM Stack (JavaScript, API, Markup)의 부상

과거의 웹사이트는 사용자가 "야후" 홈페이지를 누를 때마다 서버가 일일이 하드디스크의 데이터베이스를 뒤져서 화면(HTML)을 실시간으로 꿰매어(렌더링) 보여주었습니다. 하지만 사람이 많이 몰리면 서버가 터져버리는 고질적인 문제가 있습니다.

이러한 중앙 복잡성을 박살 내고, 모던 웹 프론트엔드의 성능을 극한으로 끌어올리는 혁명적인 구조가 바로 **JAM Stack** 입니다.

---

## 1. JAM Stack의 3대 요소

| 요소 | 설명 |
| :--: | :-- |
| **J** (JavaScript) | 브라우저 단에서 사용자와 상호작용하는 모든 동적 로직을 오직 JS만으로 처리합니다. |
| **A** (API) | 복잡한 백엔드 계산이나 DB 데이터는 개발자가 직접 구축하지 않고, 외부에 잘 만들어진 마이크로서비스(예: 결제 API, 날씨 API 등)를 가져다 플러그인처럼 씁니다. |
| **M** (Markup) | 사용자가 접속할 때마다 화면을 그리는 게 아니라, **미리 100% 다 그려놓은(Pre-Render)** HTML 뭉텅이를 사용합니다. |

## 2. 전통적 웹 vs JAM Stack 의 차이

* **전통적 웹 (WordPress, PHP, JSP 등)**
  : 접속 -> 서버가 PHP 작동 -> DB 조회 -> 서버에서 HTML 조립 -> 브라우저 던짐. (사용자가 기다려야 하며, 서버 부하가 막심함)
* **JAM Stack (SSG 체계)**
  : 개발자가 코드를 배포하는 순간, 화면(HTML) 수천 장을 미리 공장에서 찍듯이(Build) 완성해 놓습니다. 사용자가 접속하면 이미 완성되어 있는 HTML 텍스트 쪼가리를 빛의 속도로 던져주기만 합니다. 

---

## 3. JAM Stack의 명백한 장단점

### 엄청난 장점 (장악의 이유)
1. **극강의 초고속 속도:** 사용자가 누르자마자 0초 만에 (CDN 캐싱 등을 통해) 미리 만들어진 화면이 바로 뜹니다.
2. **저렴한 서버 비용 & 스케일링 무한대:** WAS나 DB 서버를 굴릴 필요 없이 전 세계에 뿌려진 글로벌 CDN 서버 위에서 정적 HTML 파일만 호스팅하면 되기에 엄청난 운영비 절감을 가져옵니다. 
3. **완벽한 보안 망:** 털릴 만한 복잡한 백엔드 서버(DB)와 통신 구조 자체가 없고 오직 API만 붙이므로 공격 포인트 자체가 없습니다.

### 치명적 단점 (한계점)
1. **빌드 속도의 늪:** 게시판 글이 10만 개라면, 코드를 조금 수정할 때마다 10만 장짜리 HTML 화면을 다시 미리 다 구워내야(Build) 하기 때문에 업데이트에 매우 오랜 시간이 걸립니다.
2. **주식 차트 등 실시간 변경 한계:** 주식 가격, 실시간 채팅처럼 0.001초 단위로 바뀌는 동적 서비스는 이미 구워진(미리 만들어진) 정적 HTML의 개념과 상극이라 맞지 않습니다.

> 실무 적용: React 기반의 `Next.js`나 Vue 기반의 `Nuxt.js`, 정적 블로그 툴인 `Jekyll` 등을 Vercel이나 Netlify 같은 클라우드에 연동해 클릭 한 번에 자동 배포(CI/CD)하는 조합이 현재 이 바닥의 진리입니다.
