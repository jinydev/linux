# 라이브 즉시 배포 전략: GitHub-Flow

복잡하고 거대한 `Git-flow`의 5가지 브랜치 전략(master, develop, release 등)이 모바일 앱이나 현대 웹서비스의 "하루에도 수십 번씩 업데이트하는" 빠른 호흡에 들어맞지 않자, GitHub 본사에서 주창한 **최단기 고속 배포 단순화 전략**입니다.

## 1. GitHub-Flow의 핵심 철학 (단순함과 CI/CD)

* **배포 브랜치의 일원화:** `develop`, `release` 같은 중간 거쳐 가는 방이 없습니다. **오직 `master`(main) 브랜치 단 하나만 존재**하며, 이 master 브랜치는 "무조건 당장 고객에게 배포해도 에러가 안 나는 무결점 상태"여야 합니다.
* **CI/CD 자동화 필수:** 누군가 master에 코드를 병합(Merge)하는 순간, 사람이 쉘 스크립트를 돌리는 게 아니라 GitHub Actions 같은 봇이 코드를 감지하고 스스로 컴파일하여 라이브 서버로 자동 배포(자동화)시키는 환경이 전제되어야 빛을 발합니다.

---

## 2. GitHub-Flow의 6단계 실무 파이프라인

복잡한 룰 대신 아래의 심플한 직선 라이프사이클을 따릅니다.

### 1단계: 브랜치 생성 (Branching)
버그를 잡든, 빅 기능을 구상하든 무조건 **최신 `master` 방에서 새 브랜치를 따옵니다.**
이때 방 이름은 `feature-login` 처럼 기능 브랜치니 뭐니 구분할 필요 없이 자유롭게 본인 의도가 명확한 식별자(예: `fix-typo-in-header`, `add-kakao-pay`)로 만듭니다.

### 2단계: 개발 및 커밋 (Commit)
내 브랜치 방 안에서 열심히 로직을 구현합니다. 로컬 컴퓨터에만 담아두지 말고, 수시로 원격지(Origin)로 Push하여 동료 서버 관리자가 내 코드를 백업하고 열람할 수 있게 만듭니다.

### 3단계: PR 생성 (Pull Request)
내 개발이 다 끝났고 라이브에 적용할 준비가 되었다면, GitHub 등 웹사이트에 들어가 `master` 브랜치 앞으로 **"내 코드를 제발 당겨가서(Pull) 합쳐주세요" 라는 요청서(PR)**를 작성합니다. 

### 4단계: 리뷰 및 토의 (Review)
PR이 올라오면 슬랙 등에 알림이 가며 수석 엔지니어나 동료들이 내 코드를 마우스로 긁어보며 피드백을 남깁니다. "이 부분 for문 성능 고치세요" 라고 하면, 나는 다시 내 브랜치에서 코드를 고치고 또 푸시(Push) 합니다.

### 5단계: 권한 승인 및 최종 테스트
모든 리뷰어의 승인(Approve)을 받으면, 가상 서버(스테이징) 환경에서 빌드가 깨지지 않는지 봇이 녹색 불(PASS)을 띄워줍니다. 

### 6단계: 최종 합병 (Merge) 및 라이브 즉시 배포
코드 리뷰가 끝난 내 브랜치의 수정보일이 드디어 `master`에 합쳐집니다(Merge).
GitHub-Flow의 최대 규칙! **"Master에 합쳐졌다면 그 코드는 사람을 기다리지 않고 그 즉시 1분 내로 무조건 라이브 넷플릭스, 구글 서버로 자동 배포되어야 한다"**는 트리거 규칙을 타고 배포됩니다. 기능 개발 브랜치는 즉시 삭제합니다.
