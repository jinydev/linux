# 업무 트래킹 도구: GitHub Projects & Issues

개발자 10명이 모여 리눅스 서버와 웹 애플리케이션을 개발할 때, 누가 어떤 코드를 짜고 있는지, 버그 수정은 어디까지 진행되었는지 파악하는 가상 프로젝트 칠판(Kanban Board)이 필요합니다. GitHub에서 제공하는 강력한 내장 협업 툴킷의 활용법을 다룹니다.

---

## 1. 이슈(Issues): 모든 작업의 출발점

단순 잡담이나 코드의 변경사항이 아닌 가치 있는 모든 **기능 추가, 버그 신고, 아이디어 멘션** 등은 철저히 하나의 "이슈(Issue) 티켓"으로 생성되어야 합니다. 개발자들은 이 티켓 번호를 물고 들어와 코딩 작업을 진행합니다.

1. **오픈(Open)과 클로즈(Closed):** 이슈(과제)를 발제하면 Open 상태가 되며, 코딩을 마치고 서버에 머지가 완료되어 임무를 완수하면 Closed(닫음) 처리됩니다.
2. **Assignees (담당자 할당):** "로그인 500 에러 고치기"라는 이슈를 생성할 때, 해당 업무를 처리할 사람을 팀원 중에서 지목합니다.
3. **Labels (태그 라벨링):** 이 티켓의 성격이 `Bug`(오류)인지, `Enhancement`(신규 기능)인지, `Documentation`(매뉴얼 작성)인지 시각적 색상의 라벨 꼬리표를 달아 분류합니다.

---

## 2. 프로젝트(Projects): 칸반 보드 시각화표

수십 개의 이슈(티켓)들이 현재 진행 중인지, 아예 손도 안 댔는지 표 형태로 묶어서 관리하는 곳이 바로 **프로젝트 탭(칸반 보드)**입니다.

### [칸반 레이아웃 파이프라인]
보통 하나의 프로젝트 보드를 파면 아래와 같은 단계별 기둥(Column) 베이스가 제공됩니다.
* **To Do (대기열):** 새로 발제되었지만 아직 아무도 작업 코딩을 시작하지 않은 대기 상태 티켓들.
* **In Progress (작업 중):** 담당자가 코드를 치면서 로컬 리눅스에 만지작거리고 있는 중인 티켓들. (PR이 올라가거나 커밋이 올라가면 이쪽으로 이동함)
* **Done (완료):** 버그가 퇴치되어 Master 브랜치에 안전하게 병합(Merge)되었거나, 영원히 закрыть(Closed) 된 완료 상태들.

📌 **자동화 (Automated Kanban):** 
엔지니어가 PR을 닫고 메인 브랜치에 코드를 합치면(Merged), 내가 굳이 마우스 조작을 하지 않아도 Github 봇이 알아서 "In Progress" 에 있던 이슈 카드를 집어 들어다가 "Done" 기둥으로 자동으로 옮겨버립니다. 

---

## 3. 마일스톤(Milestone): 여정의 챕터(버전) 나누기

마일스톤은 고속도로의 남은 킬로미터(이정표)를 뜻합니다. 큰 프로젝트에서는 모든 이슈를 한 통에 담지 않고, **"특정 날짜까지 도달해야 하는 중간 보스급 목표 버전"**으로 티켓들을 묶습니다.

* **예시:** `[버전 1.0 런칭 - 10월 30일까지]` 라는 마일스톤 폴더를 하나 만듭니다.
* 그다음 출시를 위해 꼭 필요한 로그인 버그, 결제망 구축 등 필수 이슈 10개를 이 마일스톤 안에 배속시킵니다.
* 개발자들이 이슈 하나씩을 끝내고 Closed 시킬 때마다, 마일스톤의 프로그레스 진행률(Progress Bar) 퍼센티지가 `10% >> 40% >> 100%` 방향으로 차오르게 되어 제품 출시 임박도를 한눈에 확인할 수 있습니다.
