# B2B 다중 배포 환경 트래킹: GitLab-Flow

`GitHub-Flow`가 "마스터 브랜치 하나에서 무조건 라이브 서버로 즉시 폭격 배포"하는 극단적 단순함을 지향했다면, **GitLab-Flow**는 기업들의 복잡한 테스트 서버(Staging 환경)와 출시 버전을 조율하기 위해 주창된 혼합형 파이프라인 전략입니다.

---

## 1. GitLab-Flow의 탄생 배경과 목적

GitHub-Flow는 너무 짱구같아서, 엔터프라이즈(B2B) 솔루션 개발사들은 큰 불만을 가졌습니다. 
> "우린 앱스토어 심사 때문에 내일 당장 배포할 수 없는데?"
> "우린 고객사 A, 고객사 B용으로 따로 납품 버전을 여러 개 동시 유지해야 하는데?"
> "마스터에 합쳤다고 무조건 1분 만에 라이브에 나가는 건 너무 무서운데 환경 브랜치를 나눌 수 없나?"

GitLab-Flow는 이 빈틈을 노려, 코드의 **구현(feature)** 단계와 **배포(Environment)** 단계를 물리적 브랜치로 분리하고 중간에 테스트 기착역(Staging)을 의무화시킨 진화된 룰을 만들었습니다. 

---

## 2. 브랜치(Branch) 설계 아키텍처

GitLab-Flow에서 브랜치는 위에서 아래로 물이 흐르듯 연속적인 계단 폭포수 구조를 가집니다.

### 1) Feature 브랜치 (코딩 전선)
모든 개발은 `master`에서 가지나무를 친 `feature/-` 에서 시작됩니다. 로컬 PC에서 작업하고 푸시합니다.

### 2) Master 브랜치 (통합 및 알파 테스트)
전통적인 Git-flow의 `develop` 방과 똑같은 포지션입니다. Feature 브랜치들의 코드가 매일 끝없이 병합되며 섞이는 곳입니다. 이곳이 컴파일되면, 사내 개발자들만 들어갈 수 있는 내부 테스트 망에 자동 배포되어 기초적인 버그를 잡습니다. 결코 고객 라이브 화면에 배포되지 않습니다.

### 3) Pre-Production 브랜치 (스테이징/베타 테스트)
Master에서 대충 코드가 안정화되면 바로 런칭하지 않고, 본 서버와 똑같은 DB 환경을 미러링해 둔 가상 서버, 이른바 **스테이징 환경 전용 브랜치**로 코드를 한번 더 넘깁니다. 이곳에서는 전문 QA 부서나 테스터 사용자들만이 코드를 최종 검수하고 심의합니다. 

### 4) Production 브랜치 (최종 릴리즈/본 서버)
Pre-Production 테스트 기간이 완화되고 합격 사인이 떨어지면, 드디어 이 코드를 긁어서 제일 상층부인 `Production` 브랜치로 넘깁니다(Merge). 이 Production 브랜치가 병합되는 순간이야말로 진짜 고객의 접속 서버가 패치되는 진실의 순간입니다.

---

## 3. 릴리즈 유지보수 체계 (Upstream First)

앱스토어나 패키지 소프트웨어를 팔 경우, 옛날 버전 `버전 2.3`, `버전 2.4` 브랜치들을 보존해 둡니다.
만약 과거 옛날 버전(`2.3`)에서 치명적 버그가 터졌을 때 어떻게 할까요?

* **원칙 타파 (Upstream First):** GitLab-Flow는 무조건 현재 내가 개발 중인 최신 통나무 방인 **`master` 버전에 브랜치 버그 수정을 먼저 쑤셔 박습니다.** 
* 그다음 체리픽(Cherry-pick)이라는 명령어로 그 고친 버그 코드 패치 한 조각만 핀셋으로 집어서 옛날 `2.3 Release` 브랜치 방으로 복사해 붙여넣습니다. (과거 버전에서 고치고 최신 버전으로 버그가 자꾸 올라오는 역행을 차단하기 위함입니다.)
