# 데이터베이스 패러다임: SQL 구조 기반 (RDBMS) vs 비정형 분산 (NoSQL)

MySQL, Oracle 같은 전통적인 `RDBMS`의 지배를 받던 리눅스 백엔드 생태계 시장에, MongoDB, Redis, Cassandra 같은 `NoSQL`이 등장하며 각자의 강점으로 영토를 분할했습니다. 둘 중 뛰어난 절대 강자는 없으며, 아키텍처의 서비스 성격에 따라 혼용되어 사용됩니다.

---

## 1. RDBMS (관계형 데이터베이스 / SQL)
엑셀과 같은 2차원 표(Table)에 데이터를 직각으로 깎아 넣고, 각 테이블 간의 '학번', '주민등록번호' 같은 연결고리(관계, Relation)를 단단히 채워 데이터를 관리하는 강박 주의 시스템입니다.

### [핵심 강점: 무결성과 일관성]
* **엄격한 스키마(Schema) 설계:** 회원가입 테이블에 `이름(문자열)`, `나이(숫자)` 라고 규칙(스키마)을 선언해 두면, 누군가 나이 칸에 '스무 살'이라는 문자를 적는 순간 에러를 뿜으며 삽입을 차단합니다. 
* **데이터 중복 100% 제거:** 은행 결제 등 돈이 오가는 무결성 작업에서, 회원 테이블과 결제 테이블을 쪼개두고 연결(Join)하여 데이터가 수정되더라도 양쪽에 모순이 생기지 않도록 완벽히 방어합니다.
### [핵심 한계]
* 복잡한 Join이 반복되면 쿼리 연산 CPU 트래픽이 기하급수적으로 느려집니다.
* 데이터가 너무 커졌을 때, 수평 분산 확장(컴퓨터를 여러 대 묶어 확장, Scale-out)이 구조상 기형적으로 힘듭니다. 머신 성능 자체를 비싸게 올리는 수직 확장(Scale-up)에 전적으로 의존해야 합니다.

---

## 2. NoSQL (Not Only SQL)
일정한 규격의 행과 열로 가두는 표(Table) 형식을 박살 내고, 자유로운 문서(Document: JSON)나 키-값쌍(Key-value), 그래프 등 제멋대로 치고 들어오는 유연한 덩어리를 컬렉션 단위로 부어 넣어 통째로 저장해 버리는 방식입니다.

### [핵심 강점: 초고속 유연성과 무한 확장]
* **스키마 프리 (Schema-less):** 어제는 `이름`만 있는 회원을 넣고 오늘은 `이름, 취미, 강아지 털 색깔` 이 있는 회원을 집어넣어도 불평 없이 전부 똑같은 폴더에 받아줍니다. 개발 요구사항이 매일 바뀌는 스타트업에 최고입니다.
* **압도적인 수평 확장(Scale-Out):** 거대한 표로 서로 엮인 게 없기 때문에, 유저가 폭주하면 그냥 값싼 리눅스 머신을 물리적으로 10대, 100대를 병렬로 꽂아버리면 분산 클러스터가 형성되어 속도 한계를 극복해 버립니다.

### [핵심 한계]
* Join의 개념이 없어서, 회원 정보가 여러 문서 덩어리에 파편처럼 뿌려져 담겨있을 경우 개발자가 애플리케이션단에서 일일이 찾아서 수동으로 맞춰야 합니다.
* 일관성이 깨질 위험이 있어, 1원이라도 오차가 나면 안 되는 고지식한 돈거래 금융(트랜잭션)보다는 메신저의 채팅 로그 발송 기록, 방대한 센서 수집 빅데이터를 폭탄처럼 때려 박을 때 좋습니다.

> **💡 [결론 구조]**
> * **RDBMS 지향 서비스:** 금융, 게임 아이템 결제, ERP (모순 결함을 허락하지 않는 도메인)
> * **NoSQL 지향 서비스:** 카카오톡 대화방 채팅 로그, 실시간 위치정보 쏟아붓기 추적 트래커, 세션 유지 캐시 스토어 (무한 확장성과 I/O 처리 속도가 생명인 도메인)
