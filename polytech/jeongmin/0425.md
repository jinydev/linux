# Java Virtual Machine (JVM) 동작 원리

C언어로 짠 카카오톡은 윈도우에서 컴파일하면 맥이나 리눅스에서는 뻗어버립니다. OS마다 기계어를 찰떡같이 알아듣는 CPU의 구개 구조가 다르기 때문입니다.
이를 해결하기 위해 Java 진영은 OS와 프로그램 중간에, "**OS 종류에 상관없이 자바 바이트코드를 통역해 주는 가상의 번역기 컴퓨터**" 인 **JVM**이라는 레이어를 하나 더 끼워 넣는 혁명을 일으켰습니다. (Write Once, Run Anywhere)

---

## 1. JVM의 핵심 동작 파이프라인

소스 코드(`.java`)를 치면 `javac` 컴파일러가 반쪽짜리 번역본인 바이트 코드(`.class`)를 만들어냅니다.
이 클래스 파일을 JVM이 집어삼켜서 진짜 현재 리눅스 기계가 알아먹도록 변환해 주는 3대 엔진이 돌아갑니다.

### 1) 클래스 로더 (Class Loader)
실행에 필요한 모든 `.class` 덩어리 조각들을 하드디스크에서 긁어모아 램(메모리) 위로 배치하고 엮어주는 로딩 전문 배달부입니다.

### 2) 실행 엔진 (Execution Engine) - JIT & Interpreter
로드가 끝난 바이트코드 문서를 기계어로 바꿔 읽어 내리면서 연산을 때립니다.
* **Interpreter:** 한 줄 한 줄 무식하게 읽어서 실행합니다 (전체 속도는 답답함).
* **JIT (Just-In-Time) Compiler:** 인터프리터를 보완하기 위해 나온 핵무기입니다. 자주 반복되는(For문 등) 코드는 통째로 묶어 '완전한 네이티브 기계어'로 한방에 번역 캐싱해 버리기 때문에 속도가 비약적으로 빨라집니다. 혼합 방식을 씁니다.

### 3) 가비지 컬렉터 (Garbage Collector)
C언어는 쓰레기 메모리(버려진 변수)를 `free()` 로 치워주지 않으면 서버가 죽지만, 자바는 이 청소부 봇(GC)이 메모리 더미를 24시간 감시하다가 아무도 안 쓰는 참조 끊긴 메모리 쓰레기를 스스로 빗자루질해서 공간을 확보합니다.

---

## 2. JVM의 영토: 런타임 데이터 영역 (Runtime Data Area)

JVM은 OS로부터 하도급받은 램(RAM) 공간을 다시 5개의 칸막이로 쪼개서 용도별로 변수를 관리합니다.

1. **PC Register:** 현재 스레드가 어디 코드 몇 번째 줄을 지나가고 있는지 형광펜을 칠해두는 기록 일지입니다.
2. **JVM Stack:** 메소드(함수)를 부를 때마다 `int a`, `String b` 같은 잠깐 쓰일 지역 변수를 담았다가 함수 끝나면 펑 터트려 사라지는 공간입니다.
3. **Native Method Stack:** 자바가 아닌 언어(C, C++)로 엮인 외부 라이브러리 코드를 돌릴 때 쓰는 이질적인 스택 구역입니다.
4. **Method Area (Static 영역):** 클래스 틀(붕어빵 기계), 인터페이스, Static으로 선언된 '전역 공유 변수' 들이 서버가 켜질 때 한 번에 싹 박혀있는 공용 게시판입니다. 
5. **Heap (힙 영역):** `new Person()` 처럼 개발자가 마구 찍어내는 모든 메모리 덩어리(인스턴스 객체)가 끝없이 던져지는 드넓은 공터이자 유일한 쓰레기장이요, 나중에 GC(가비지 컬렉터) 미화원이 빗자루질을 하는 유일한 공간입니다.
