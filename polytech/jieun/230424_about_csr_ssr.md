# 프론트엔드 렌더링 패러다임: SSR 과 CSR

우리 눈앞에 카카오톡 웹이나 유튜브 화면이 이쁘게 그려지는 것을 **렌더링(Rendering)** 이라 부릅니다. 과거 웹 기술은 단순히 화면을 서버에서 다 그려서 보내줬지만, 자바스크립트 엔진의 발전으로 브라우저(클라이언트)가 직접 화면을 스케치하는 시대가 되며 양대 진영이 구축되었습니다.

---

## 1. SSR (Server Side Rendering - 옛날 통닭 방식)

웹 브라우저가 화면을 달라고 요청하면, **뒷단 서버 장비(Node.js, Spring) 모델이 CPU를 돌려 HTML, CSS, 데이터 표를 완전히 그림으로 완성 조립한 뒤** 통째로 브라우저에 배달해 주는 전통적인 방식입니다. 

* **동작 파이프라인:** 브라우저 접속 -> 물리 서버가 DB 뒤져서 HTML 문서 완성(Ready) -> 브라우저 수신 및 즉시 노출 -> 이후 자바스크립트 결합.
* **압도적 강점:** 제일 빨리 화면이 뜹니다. 첫 렌더링(First Paint) 속도가 가장 빠르며 구글/네이버 검색 로봇(Crawler) 이 내용을 100% 퍼갈 수 있어서 **검색 노출 최적화(SEO)** 에 천하무적입니다.
* **단점:** 클릭해서 다른 페이지로 넘어가려고 하면, 렌더링을 처음부터 서버가 또 그리기 때문에 화면이 하얗게 껌벅(Blink)이는 깜빡임 현상이 필연적으로 생깁니다. 모든 렌더링 연산을 서버가 감당하므로 트래픽 비용과 서버 부하가 높습니다.

---

## 2. CSR (Client Side Rendering - 밀키트 조립 방식)

React, Vue, Angular가 주도권을 쥔 현대 SPA(단일 페이지 앱) 웹 생태계의 교과서입니다. 그림을 다 그려주지 않고, **서버는 텅텅 빈 스케치북(index.html)과 물감 한 바가지(거대한 JS 파일) 만 툭 던져줍니다.** 그러면 브라우저(크롬)가 접속자의 폰이나 PC CPU를 굴려서 화면을 실시간으로 직접 그려냅니다.

* **동작 파이프라인:** 접속 -> 빈 스케치북과 메인 자바스크립트 통째로 다운로드 -> 완료되면 그때 브라우저가 JS를 분석해 API(데이터)를 부르고 화면을 즉석 렌더링.
* **압도적 강점:** 처음 밀키트(JS)를 다운받고 나면 그다음부터 클릭해서 다른 카테고리를 눌러도, 서버에 갈 필요 없이 그냥 내 크롬 브라우저가 필요한 부분만 즉석에서 갈아 끼워 그리므로 마치 네이티브 모바일 앱처럼 화면 전환이 버터처럼 부드럽고 매끄럽습니다. 서버 연산의 부하가 거의 제로에 가깝습니다.
* **단점:** 최초 접속 시 뚱뚱한 JS 물감통을 내려받아야 하므로 최초 1회 빈 하얀 로딩 창(수 초간 지연 현상)이 거슬립니다. 또한 검색 봇이 텅 빈 스케치북만 가져가 버려 SEO 점수가 쓰레기가 될 위험성이 높습니다. 

> **💡 총평 요약**
> * **SSR 선호:** 네이버 블로그, 쇼핑몰 상세, 나무위키 (SEO 무한 노출 검색이 기업 생명줄인 경우)
> * **CSR 선호:** 넷플릭스 영상 패널, 인스타그램 피드, 사내 어드민 페이지 (SEO 필요 없이 화려하고 부드러운 앱 같은 유저 전환 경험이 생명일 경우)
