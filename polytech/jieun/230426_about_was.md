# 웹 서비스의 3-Tier 아키텍처: Web Server vs WAS

"사용자가 네이버나 다음 사이트에 들어왔다." 이 단순한 요청 하나 뒤에는, 속도전을 뛰는 전방 부대와 복잡한 계산을 하는 후방 특수 부대로 역할이 완벽히 조각난 서버 인프라 분산 체계가 은닉되어 동작합니다.

---

## 1. 정적 파일 배달꾼: 웹 서버 (Web Server) 
오로지 HTML 문단, 메뉴 디자인 CSS, 제니 프로필 사진(이미지 파일) 같은 **단순하고 고정된 정적 컨텐츠를 사용자 브라우저에 가장 빨리 뿌려주는 덤프 트럭**입니다. 제일 전방에서 고객을 맞이합니다.

* **동작 방식:** 손님이 `http/image/logo.png` 를 요청하면, 즉시 자기 하드디스크 창고에서 찾아서 갖다 줍니다. 반면 손님이 "게시판 조회수 올려주고 DB 업데이트해 줘!" 같이 복잡한 두뇌를 쓰는 처리를 요구하면 거부하고 후방(`WAS`)으로 던져버립니다.
* **솔루션 예시:** 세계의 양대 산맥인 `Apache (아파치)`, `Nginx (엔진엑스)`

## 2. 동적 비즈니스 처리반: WAS (Web Application Server)
사용자가 오늘 구매한 상품 총액을 계산하거나, 데이터베이스(DB)에서 은행 잔고를 까서 확인해야 하는 **복잡한 자바(PHP/Node.js) 비즈니스 연산 로직(동적 컨텐츠)을 전문으로 처리**하는 미들웨어 두뇌 부대입니다.

* **동작 방식:** 앞단의 웹 서버가 토스해 준 무거운 두뇌 연산 건을 넘겨받아 CPU를 통해 처리하고, DB 접속 풀의 통신을 열어 트랜잭션을 수술한 뒤 완성된 결과물을 다시 앞의 웹 서버로 던져줍니다. 과거 자바 환경에서는 `웹 컨테이너(서블릿)` 규격이 가장 많이 언급되었습니다. 
* **솔루션 예시:** `Tomcat (톰캣)`, `WebSphere`, `Jeus`, `JBoss`

---

## 3. 왜 굳이 Web Server 와 WAS 두 개를 찢어둘까?

옛날에는 톰캣(WAS) 하나만 달랑 깔아서 그림 파일도 응답하게 하고 계산도 시켰으나, 현대 인프라에서는 이 둘을 물리적으로 찢는(분리하는) 3-Tier 아키텍처 모델을 필수 표준으로 따릅니다. 

### 1) 부하 분산 (웹 퍼포먼스 보호)
용량이 큰 이미지를 수십만 명이 동시에 다운받아가면 서버 자원이 터집니다. 이미지 던져주는 단순 업무는 Nginx (Web Server) 선봉 부대가 다 막아내도록 시키고, 복잡하고 위험한 은행 잔액 결제 건만 뒤로 넘기면 서버 과부하 지연이 극적으로 사라집니다.

### 2) 서버 다중화 폭발 (소프트웨어적 캐시 스케일 아웃)
장사가 너무 잘 되면 웹서버(Nginx)는 앞에 하나만 두고 뒷단 결제 프로그램 WAS 덩어리들을 클러스터링으로 수십 대 병렬 로드 밸런싱 세팅을 할 수 있습니다. 

### 3) 철옹성 보안 방화벽 설계망 분리
일반 사용자의 구글 브라우저는 최전방에 위치한 `웹 서버` 까지만 도달할 수 있습니다. 진짜 비밀 돈거래를 하는 `WAS`와 `DB`는 내부 사설(가짜) IP망 방화벽 뒤쪽으로 꼭꼭 깊숙이 숨겨둘 수 있으므로 악성 해커가 소스코드를 털어가는 취약점이 원천 봉쇄됩니다.
