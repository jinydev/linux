# 인프라 협업의 법률: Git 커밋 & PR 컨벤션

나 혼자 개발하는 메모장이 아니라면, 100명의 개발자가 하나의 프로젝트(Repository) 코드를 동시에 부수고 뜯어고칠 때 '이 코드가 왜, 무엇을, 어떻게 수정했는지' 로그 장부를 명확히 남기기 위한 전 세계 공통의 텍스트 규약(Convention)입니다. (대표적으로 널리 쓰이는 Udacity 스타일 가이드를 따릅니다.)

---

## 1. Commit 메시지 아키텍처 (장부 작성법)

단순히 `커밋 메시지: 아 힘들어` 라고 적으면 3개월 뒤의 나와 동료 개발자를 분노케 합니다. 커밋 메시지는 엄격한 헤더(Type: Subject)와 바디(Body), 꼬리(Footer) 파트로 수직 정렬되어야 합니다.

```text
[type]: [Subject] (무엇을 했는지 영문 명령형 50자 이내)

[body] (왜 이 짓을 했는지 상세 문맥 서술 72자 이내 줄바꿈)

[footer] (참조 이슈 트래커 티켓 번호 매핑)
```

### [Type]의 명확한 행동 선언
이 커밋 덩어리가 전체 서비스에 무슨 영향을 주는지 첫 단어로 박아 넣습니다.
* **`feat:`** 새로운 기능(Feature)이 추가되어 서비스 창조가 일어났을 때.
* **`fix:`** 운영 서버를 태워 먹던 치명적인 버그/오류를 수정(Patch)했을 때.
* **`refactor:`** 기능은 100% 똑같은데, 내부 스파게티 소스코드를 예쁘게 최적화(Refactoring)만 쳤을 때.
* **`chore:`** 로직이 아니라 젠킨스(CI/CD) 설정이나, 패키지 버전(npm 등) 잡동사니를 건드렸을 때.
* **`style:`** 세미콜론(;) 누락 같은 단순 띄어쓰기 포맷팅만 했을 때.
* **`docs:`** README 파일이나 주석 메모 등 문서만 수정했을 때.

## 2. PR (Pull Request) 컨벤션 : 합병 승인 결재 서류

내가 짠 분리된 나만의 브랜치(Branch) 로직을, 회사의 메인 운영 서버 브랜치(Main)에 합쳐달라고(Merge) 선임 개발자에게 던지는 **기안 결재 서류** 입니다. PR 메시지가 부실하면 선임은 당신의 코드를 열어보지도 않고 Reject로 반려시킵니다.

### PR 결재 서류 필수 요건 (가이드라인)
1. **최종 목적의 1줄 요약:** "장바구니 0원 결제 시 폭사하던 버그를 고쳤습니다."
2. **배경 맥락 (Context):** "이전 코드에서는 NULL 체크 로직이 타임아웃을 유발했습니다."
3. **태그 (리뷰 방향 강제):** 
   - `[WIP]` (Work In Progress): 나 아직 코드 짜는 중이니까 함부로 머지(합병)하지 마라. 구경만 해라.
   - 피드백 요구 핀포인트 지적: "로그인 세션 만료 테스트 쪽에 메모리 누수가 의심되니 이 함수를 중점적으로 까주세요."

```markdown
<!-- PR 템플릿 예시 -->
## 🚀 작업 목적
- 결제 모듈의 분산 트랜잭션 오류 픽스

## 🛠 수정된 로직 상세
- API v2 호출 시 헤더 누락 부분 추가 `src/auth.js`
- 관련 유닛 테스트 3종 추가 통과 완료

## 📝 리뷰어가 집중해서 봐줬으면 하는 부분
- 비동기 처리 콜백 쪽에서 Race Condition 이 터질지 한번 더 정밀 코드 리뷰 부탁드립니다.

## 🔗 관련 이슈 티켓
Closes #402, Resolves #109
```
