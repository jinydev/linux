# 형상 관리의 뼈대: Git 아키텍처와 저장소의 탄생

코드를 짜다 폭파시키고 `Ctrl+Z`를 연타하는 원시적인 개발을 탈피하고자, 리누스 토발즈(Linux 창시자)가 단 2주 만에 뚝딱 만들어 전 세계 인프라를 지배해버린 분산형 버전 관리 시스템(VCS)입니다. 내 컴퓨터(Local)와 깃허브 서버(Remote)를 동기화하여 언제든 과거의 완벽한 상태로 롤백(타임머신)할 수 있는 무결성 장부 역할을 합니다.

---

## 1. 저장소의 성역화: `git init` 과 `.git` 의 정체

그냥 평범한 바탕화면의 폴더에 이 명령어 한 줄을 치는 순간, 평범한 공간은 '코드의 모든 역사가 기록되는 신성한 저장소(Repository)' 로 렌더링됩니다.

```bash
# 내 폴더에 깃 생명체(추적기)를 잉태시키는 명령어
$ git init
```

* **보이지 않는 심장 `.git`:** 명령어를 치는 순간 디렉토리에 숨김 폴더인 `.git` 이 떡하니 박힙니다. 이 폴더 안에 내 코드의 모든 변경된 글자 하나하나, 그리고 과거로 돌아가는 타임머신 부품(객체 데이터베이스)들이 전부 암호화되어 압축됩니다. (이 폴더를 강제 삭제하면 당신의 코드 1년 치 과거 변경 이력들도 영구 소각당합니다.)

---

## 2. 권한의 분할: Working Directory 과 Tracked의 추적론

Git은 내 프로젝트 폴더 안의 모든 파일을 막무가내로 전부 저장하지 않습니다. 철저하게 "나 이거 감시해 줘" 라고 허락망에 편입된 놈들만 쳐다봅니다.

### [워킹 디렉토리 (Working Directory)]
여러분이 VS Code를 켜놓고 신나게 코드를 짜는 땀내 나는 작업 공간 전체를 의미합니다.
* **Untracked (미행 금지):** 방금 내가 새로 만든 `test.js` 파일은 깃 시스템 입장에서 **투명인간(Untracked)** 취급을 받습니다. 여기서 폭탄을 터뜨리든 코드를 지우든 깃은 전혀 참견하지 않고 과거 버전을 롤백시켜 주지도 않습니다.
* **Tracked (추적 시작):** 추적망에 올리기 위해 쓴 최초의 수동 명령어가 바로 `$ git add` 입니다. 이것을 친 순간 깃 데몬이 `test.js` 의 파일 텍스트 한 글자 한 글자를 스캐닝하기 시작합니다.

---

## 3. 중간 대기실의 환상: Stage (Index) 영역

왜 곧바로 최종 저장소에 저장(Commit)하지 않고 굳이 `add` 라는 귀찮은 중간 단계 버퍼(Stage)를 거치게 설계했을까요? 이는 극단의 최적화를 위한 렌더링 철학 때문입니다.

* **커밋의 미학:** 수백 개의 파일을 동시에 수정(수정된 A, B, C, 버그 투성이인 D 파일)했을 때, 깃허브에는 완벽하게 작동하는 A, B, C 파일만 먼저 예쁘게 포장해서 버전(Commit)으로 밀어 넣고 싶을 때가 무조건 생깁니다.
* **스테이징 에어리어:** 최종 결재(Commit)를 올리기 직전, 결재 서류철 폴더에 올릴 놈(A, B, C)만 집어넣고, 실패한 코드(D)는 밖(워킹 디렉토리)에 놔둘 수 있도록 멱등성 여과 장치를 제공하는 것이 바로 이 `Stage` 임시 테이블 공간입니다.
