# Git의 내부 심연: 객체 지향 데이터베이스 (Objects)

`git add`와 `commit`을 쳤을 때, 터미널에서는 딸랑 "완료" 글자만 뜨지만 `.git` 숨김 폴더의 지하실 안에서는 물리적 쇳덩어리(블록)에 어떤 데이터가 파싱되어 렌더링되는지를 완전 분해하는 엔지니어 심화 레벨 지식입니다.

Git의 코어 철학은 "변경 전/후의 파일 스냅샷 전체를 압축해서 통째로 들고 있는다" 입니다.

---

## 1. 궁극의 중복 제거: SHA-1 해싱과 Blob 객체

`git add f1.txt` (내용: `"hello"`) 를 치는 순간 깃은 끔찍한 연산과 파일 분쇄를 시작합니다.

1. 파일 내용 `"hello"` 를 읽어 들여서 무조건 40자리짜리 흉악한 해시(Hash) 암호 난수 **`c22b5...`** 로 변환시킵니다.
2. 이 해시값의 앞 2글자(`.git/objects/c2/`)로 폴더를 하나 파버리고, 나머지 38자리 글자 이름으로 파일을 생성해 그 안에 `"hello"` 라는 텍스트를 고도로 압축해 박아 넣습니다.
3. 이 본문 덩어리를 **`Blob (Binary Large Object)`** 이라 부릅니다.

* **미친 중복 제거 능력:** 만약 파일명이 `a.txt`, `b.txt`, `c.txt` 이고 세 파일의 본문 내용이 모두 `"hello"` 로 똑같다면? 깃은 바보같이 용량을 3배로 늘리지 않습니다. "어? 해시 돌려보니 전부 `c22b5..` 값이네?" 라며 단 1개의 Blob 파일만 쇳덩어리에 올리고, 인덱스(Index)라는 방명록에 **"a, b, c 세 놈 모두 저 `c22b5` 블록 덩어리를 꺼내 읽어라"** 라며 포인터 링크만 공중 연결(Symlink-like) 시킵니다.

---

## 2. 폴더 뼈대의 기억: Tree 객체 (스냅샷 디렉토리)

파일 본문을 파쇄해서 Blob 덩어리로 만들었다면, 이 수백 개의 파일들이 "어떤 폴더 소속이었고, 파일명이 뭐였는지" 의 껍데기 이름표들을 묶어주는 디렉토리 추상화 객체입니다.

* `git add` 시점의 폴더 구조와 파일 이름들(f1.txt, f2.txt 등)을 트리(Tree) 구조체에 파싱해서 저장합니다.

---

## 3. 영구 박제 렌더링: Commit 객체의 탄생

내 컴퓨터에서 최종 결재 도장인 `git commit -m "첫 번째 버전"` 을 내려찍는 순간, 이 짓거리들의 최종 조립 마무리가 들어갑니다.

* **커밋 객체(Commit Object)의 구성 부품:**
  1. **Tree 정보:** 이 버전에서 내가 완성시킨 전역 디렉토리 트리들의 최꼭대기 Root 포인트 링크.
  2. **Parent (부모):** 내가 이 코드를 고치기 바로 직전인, 옛날 과거 버전 커밋의 해시 ID 주소값 연결 (이 체인이 끊어지면 타임머신 역추적 불가).
  3. **메타데이터:** `수정 날짜`, `수정한 사람 이메일/이름`, 그리고 `"첫 번째 버전"` 이라는 개발자의 코멘트 텍스트.

이 3가지 부품을 조립해 **거대한 커밋 해시 ID(예: `7e9f3...`)** 를 발급해 버립니다. 나중에 우리가 깃허브에서 `git reset 7e9f3` 로 시간 여행 롤백을 때리면, 깃은 이 부모 체인 배열을 타고 내려가 당시 시점의 Tree를 복구하고 Blob 본문을 풀어서 내 눈앞 폴더에 부활시켜 줍니다.
