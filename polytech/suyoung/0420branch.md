# 형상 관리 분할의 궁극: 브랜치 (Branch & HEAD) 구조 

10명의 엔지니어가 하나의 메인(Main) 코드 서버에서 로그인 기능, 결제 기능, 게시판 기능을 동시에 코딩하다간 서로 코드를 덮어쓰고 꼬여서 하루 만에 폭동이 일어납니다. 

기존의 안정적인 운영 서버 코드 줄기(Master/Main)는 놔둔 채, 각자 자기만의 평행 우주 가지(Branch)를 찢어내어 파생시킨 뒤 버그 똥을 치우고 나중에 조립 결합(Merge)하게 해주는 멀티버스 복제 아키텍처입니다.

---

## 1. 브랜치의 실체: 달랑 커밋 주소값 텍스트 파일 1줄

`$ git branch exp` 라는 명령어로 평행우주 가지를 분리해 뻗어냈을 때, Git 폴더 내부에 용량이 2배로 불어나고 소스코드가 복제되는 끔찍한 오버헤드는 절대 일어나지 않습니다.

**브랜치의 정체는 그저 포인터 주소 스티커일 뿐입니다.**
* `.git/refs/heads/` 디렉토리 아래에 `master` 도 있고, 방금 쳐 만든 `exp` 라는 이름의 깡통 파일이 하나 생성됩니다.
* 이 `exp` 파일을 열어 까보면 텍스트 소스코드가 들어있는 것이 아니라, `7e5f3z...` 같은 40자리 해시 난수 1줄만 딱 적혀 있습니다.
* 즉 브랜치란, **"니가 가장 최근에 결재 완료한 최고 최신버전 커밋(Commit Object)이 뭐임?"** 을 외우고 손가락 포인트로 가리키고만 있는 용량 41바이트짜리 무지성 이정표에 불과한, 극도로 미니멀한 렌더링 아키텍처입니다.

---

## 2. 권력의 중심점: `HEAD` 나침반 포인터

브랜치가 100개가 생기면, 내 터미널(VS Code) 화면에서는 100개 중 도대체 어떤 우주의 소스코드를 렌더링해서 띄워줘야 할지 컴퓨터가 당황하게 됩니다.

이때 **'내 심장(내가 보고 있는 화면)이 100개 브랜치 중 어디를 가리키고 있는가'** 를 증명해 주는 대빵 포인터 파일이 바로 `.git/HEAD` 파일입니다.

### [HEAD가 브랜치를 추적하는 워크플로우 매커니즘]
1. `.git/HEAD` 를 열어보면 해시값이 아니라 `ref: refs/heads/master` 같이 어느 지부(브랜치) 소속인지만 적혀 있습니다.
2. 만약 내가 `$ git checkout exp` (우주 워프 이동!) 를 치는 순간.
3. `.git/HEAD` 파일 내용이 `ref: refs/heads/exp` 로 갈아 끼워집니다.
4. 이제 깃은 `exp` 파일 안에 적혀있는 해시 커밋 객체 덩어리를 찾아낸 뒤, 그 안에 압축되어 있던 소스 코드 본문(Tree, Blob) 파일 수천 개를 하드디스크에 파라락 압축 해제해서 내 눈앞에 부활 렌더링시켜 줍니다.

---

## 3. 분기 선상 충돌의 미학 (Log 시야각 확보)

각자의 우주(브랜치)에서 커밋을 쌓아 올리다 보면, 어느 순간 평행우주 간의 코어가 완전히 찢어져 다르게 흘러갑니다.
이때 터미널에서 `$ git log` 만 치면 내가 있는 우주의 역사만 보여서 상황 파악이 안 되므로, 반드시 3차원 멀티버스 전체를 조망하는 해킹 옵션을 탑재해야 합니다.

```bash
# --branches: 모든 분기 우주 트리를 다 가져와라
# --decorate: 어느 커밋에 브랜치 포인터(이표정) 딱지들이 붙어있는지 보여라
# --graph: 찢어지고 합쳐진 우주선 궤도를 텍스트 렌더링(---*---)으로 시각화 터뜨려라!
$ git log --branches --decorate --graph --oneline
```
