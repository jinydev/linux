# CPU 스케줄링 알고리즘 (FCFS / SJF)

멀티태스킹 운영체제(리눅스, 윈도우 등)에서, 동시에 수십 개의 프로그램이 실행되려 할 때 한정된 CPU(두뇌)를 어느 프로그램에게 먼저 배정해 줄 것인가를 결정하는 교통정리 기술이 **'CPU 스케줄링(Scheduling)'**입니다.

| 지표 | 설명 |
| :-- | :-- |
| **대기 시간 (Waiting Time)** | 프로세스가 CPU를 받기 위해 줄을 서서 가만히 기다린 총 대기 시간입니다. |
| **실행 시간 (Burst Time)** | 프로세스가 실제로 CPU 위에서 뛰어놀며 연산 작업을 수행한 시간입니다. |
| **반환 시간 (Turnaround Time)** | 대기 시간 + 실행 시간을 합친 값으로, **작업이 완전히 끝날 때까지 소요된 총 통과 시간**입니다. |

---

## 1. 선입선처리 (FCFS: First-Come, First-Served)
> 식당에 줄 선 순서대로 밥을 먹는 가장 정직하지만 답답한 방식입니다.

* **특징:** 먼저 요청한 프로세스가 CPU 자원을 할당받으며, 뺏기지 않는 **'비선점형(Non-preemptive)'** 스케줄링입니다.

### 시뮬레이션 예시
| 프로세스 | 도착 시간 | 실행 시간(수행량) |
| :---: | :---: | :---: |
| **P1** | 0초 | 3 |
| **P2** | 1초 | 2 |
| **P3** | 2초 | 1 |

* **작행 흐름 (Gantt Chart)**
  * `[0초 ~ 3초]` **P1 실행 (완료):** 대기 = 0 / 통과 반환 = 3
  * `[3초 ~ 5초]` **P2 실행 (완료):** P2는 1초에 도착했으나, P1이 끝나는 3초까지 기다렸음 (대기 = 2) / 통과 반환 = 4
  * `[5초 ~ 6초]` **P3 실행 (완료):** P3은 2초에 도착했으나 P1,P2의 종료인 5초까지 무려 3초를 기다렸음 (대기 = 3) / 통과 반환 = 4

* **평균 성능:**
  * 평균 대기 시간: `(0 + 2 + 3) / 3 = 1.67초`
  * 평균 반환 시간: `(3 + 4 + 4) / 3 = 3.67초`

* **치명적 단점 (호송 효과 / Convoy Effect):** P1 같이 무식하게 큰 파일 다운로드(100분짜리)가 제일 먼저 들어오면, 뒤에 1초면 끝나는 간단한 작업(마우스 클릭 등)이 앞에 처리가 끝날 때까지 100분을 대기해야 하는 최악의 효율이 발생합니다.

## 2. 최소 작업 우선 스케줄링 (SJF: Shortest Job First)
> "작업량이 가장 적은 놈부터 빨리 끝내버리자!"

* **특징:** 도착 순서와 상관없이 큐에 쌓인 애들 중에서 **'CPU 실행 길이'가 가장 짧은 프로세스에게 우선권**을 줍니다. 대기열의 평균 대기시간을 수학적으로 가장 짧게 만드는 꿈의 알고리즘입니다.

### 시뮬레이션 예시 (비선점형 SJF)
* P1이 3초 어치를 수행 중인 상황이라 가정. P2(2초 실행), P3(1초 실행)가 대기하고 있습니다. 
* FCFS였다면 들어온 순서대로 P2부터 처리하겠지만, SJF는 P1 종료 시점에 P2, P3를 비교해 **더 짧은 P3부터 무조건 끼워 넣어 처리**해 버립니다.

* **치명적 단점 (기아 현상 / Starvation):** 엄청나게 덩치가 큰 무거운 작업(예: 4K 렌더링)은 뒤에 계속해서 가벼운 작업들이 들어온다면 끝도 없이 양보만 하다가 **영원히 실행되지 못해 굶어 죽어버리는 현상**이 발생합니다.
* **현실적 한계:** 운영체제는 Pn 이라는 프로세스가 앞으로 정확히 몇 초간 CPU를 쓸지 '미래'를 완벽하게 예측할 수 없으므로 현실에서 구현이 불가능한 탁상공론 알고리즘에 가깝습니다. (다만 예측 근사치를 통해 유사 구현합니다)
